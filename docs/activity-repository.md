# Activity repositories and read projections

Open when changing activity durability, account ownership, upload acknowledgements, or activity-driven plan/statistics refresh. `performed-workout-sync.md` owns exact issued-recipe attribution; `account-calendar.md` owns calendar policy; `account-statistics.md` owns complete account totals.

## Durable source and ownership

- `ActivityPersistence` is the serialized writer. `activities.json` is an atomic manifest envelope containing each activity, its exact private receipt, account owner, mutation generation and sync state. Existing photo JPEGs and route sidecars remain files; no database rewrite or image reencoding is introduced.
- Save returns after the manifest commits. The observable repository snapshot contains the committed rows and completion/reconciliation projection together. Screens consume these read models; saving does not depend on opening Today, Plan Details or Me.
- Every asynchronous activity adapter captures an account context before suspension. Manifest operations, token acquisition, 401 replay, response publication and session refresh validate that context. Credential replacement/signout also fence old refresh completion. Account caches use account namespaces; statistics use a `monday-v1` namespace independent of device travel.
- Goal and personalization observers are owned by the coordinator. Personalization refresh runs after the activity sync pass, and its cache/queued mutations are account-scoped and fenced; prior global personalization queues remain unclaimed.
- Guest rows remain guest. Legacy global rows become `legacy-unverified` without deleting files. They stay quarantined until an authenticated response verifies **both** their existing server ID and client UUID. Verified rows retain original local media. Unverified legacy pending work remains on disk and is not automatically uploaded or claimed; a user-facing ownership recovery workflow is not implemented.
- Account deletion removes only that account's manifest entries and media no other owner references. It preserves guest/quarantined/other-account rows. Local history deletion retains server-confirmed completion association evidence, matching the backend's existing deletion semantics.

## Exact completion projection

- Pending completion is derived from the same durable activity receipt and deduplicated by exact planned-workout ID. Free runs, imports without receipts, matching dates and durations never infer completion.
- Pending saved work is labeled separately from server-confirmed completion. A terminal `409 performed_workout_conflict` retains the activity/reference, withdraws optimistic credit, persists a typed rejection and suspends automatic upload retries. The failure banner provides an explicit retry command; edits also create a fresh mutation generation.
- Overlay only known IDs in the authoritative schedule. Count current scheduled prescription minutes for plan progress; actual saved duration belongs to history, and retained issued duration remains acknowledgement metadata. Neither pending nor confirmed presentation advances the local programme/source dose.
- Authenticated offline mode retains the last authoritative schedule. It never calls the local recommendation engine to infer completions. Account Monday rollover re-buckets cached logical date keys, recomputes counts and expires stale Today suggestions. Exhausted cached coverage explicitly asks to connect; it does not assert a known empty week.

## Acceptance and reconciliation

- Activity create/update/dedup transactions hold the planning-user lock and return `reconciliation` with `planningRevision`, `statisticsRevision` and the exact canonical completion association or null. Association and watermarks are captured **inside** that accepted transaction.
- `User.planningStateRevision` is a serialized **observation watermark**. Assembling a planning snapshot also increments it under the same lock. It is deliberately not a count of all source mutations. A later snapshot is ordered after an accepted activity; clients reject lower snapshot revisions. Plan version remains a separate prescription concept.
- The authoritative per-account planning and complete statistics baselines are encoded in the atomic manifest. A read revision is accepted only after its baseline commits; statistics writes also check their invalidation ticket; accepted planning commands atomically persist their baseline and statistics invalidation. UserDefaults is incidental/guest cache, not the acknowledgement boundary.
- Upload acceptance, sync state, confirmed association and remaining read cursor commit atomically. Failed acknowledgement persistence propagates an error and retains pending work. If an activity changed during upload, the old generation can retain acceptance evidence but cannot mark the new generation synced or overwrite it.
- Canonical identity adoption prepares copied JPEGs and remote photo placeholders before one manifest switch. Every sidecar overwrite first writes a durable before-image journal for the existing target route, elevation metadata and original route. Before any manifest read, recovery rolls back uncommitted sidecar writes or discards the journal after detecting the committed source removal/target generation. This also protects existing targets across process crashes. Atomic upload snapshots capture payload and generation together; sync metadata, remote baselines and photo metadata use actor-side conditional/current-row writes to preserve later edits and manual photo order. It checks source and target generations; source media is removed only after durable adoption. Failed preparation/publication leaves the original manifest identity intact.
- The app-lifetime `ActivitySyncCoordinator` observes committed snapshots and accepted plan commands, and resumes on activation/connectivity/day/significant-time changes. Upload and remaining planning/statistics reads use bounded retry. Accepted uploads do not need to repeat solely because a downstream read failed.
- Backend complete statistics snapshots remain the only authenticated aggregate authority; no local deltas are added. Accepted planning commands durably invalidate their statistics read model. A persisted invalidation generation/read ticket prevents an older in-flight read from clearing a newer command's dirty state, even when activity statistics revisions are equal.

## Android Room repository

- Room v9 (`plainstride-v9.db`) atomically stores each activity's mutation generation and serialized outbox payload, its exact private receipt/completion association, the authoritative per-account planning/statistics baselines, required server revision cursors and statistics invalidation ticket. A null planning baseline means unknown; a committed snapshot with no plan is a known empty state.
- `AccountReadRepository` projects the same durable planning baseline for Today and Me. Only receipt-linked exact IDs already present in the authoritative schedule receive pending/confirmed credit. Pending is labeled separately in Today and Plan Details; saved exact recipes are withdrawn from Today launch suggestions while other/freestyle recipes remain available. A state-level guard covers asynchronous planning/suggestion emissions. Progress minutes remain the current scheduled prescription. Canonical confirmation overlays bridge only an older baseline; a planning snapshot at or beyond the association acceptance revision owns the final status. No free-run matching, source-week advancement or local statistics delta is added.
- Upload acknowledgement adopts canonical identity/media and commits acceptance/cursors before removing the captured outbox generation. Later activity edits remain pending. Canonical JPEGs are copied without decoding; routes, original routes, ordered photo metadata and the manifest switch use one Room transaction. Source files are removed after that switch. A failed preparation retains the source identity; stale server metadata cannot overwrite a pending local mutation.
- A `409 performed_workout_conflict` retains the activity/reference, withdraws pending credit and persists a rejected operation. Automatic upload retries stop; the persistent connectivity banner offers Retry. Editing creates a fresh generation. Bounded analytics use `activity_sync_failed` with `performed_workout_conflict`, and `feature_exposed` with `performed_workout_retry`; identities, receipt data and activity values are excluded.
- Session epochs fence token acquisition, async response publication, canonical/metadata/photo writes and credential refresh completion, including a switch away and back to the same account. HTTP 401 remains a retained failed operation; no unfenced automatic replay is introduced.
- `AccountRepositoryCoordinator` observes account/outbox/read changes for the app lifetime, resumes on foreground/connectivity and checks time each minute. WorkManager also resumes durable uploads and outstanding planning/statistics reads. Read retry is bounded per pass; downstream failures retain dirty cursors without re-uploading acknowledged activities. Complete backend totals remain authoritative. An old statistics ticket cannot clear a later command's invalidation even at the same statistics revision.
- Calendar projections re-bucket logical schedule dates at account Monday rollover, clear an old Today workout and expired suggestion recipes/alternates reactively, and retain partial Week 1. Exhausted cached coverage asks to connect; it does not claim an empty week. A previously confirmed no-plan snapshot stays distinct from an unknown baseline while offline.
- Unreleased Android policy: v9 opens clean local data and does not migrate/copy v8 activities, preferences, journals or outbox. Backend data remains intact. Rebuild: `cd android && ./gradlew :app:assembleDebug`. Full optional development reset: `adb shell pm clear com.plainstride.outbound.debug`.
